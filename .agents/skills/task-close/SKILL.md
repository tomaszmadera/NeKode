# Task close

Inputs from the owning workflow include the task record and one verification mode: `none`, `already-complete`, `targeted`, `changed`, or `full`.

1. `already-complete` is close-only. Before the first mutation, confirm that the latest `verify` Timing row is closed and its Verification evidence records a pass, then run recorded `commands.verification_subject` with `check --record <task-record>`. If that evidence is incomplete, the latest immutable subject is absent, or the subject does not match exactly, leave the task active and return the evidence to the owning workflow. Do not open retro, run `lesson-select`, edit another file, or rerun verification on this path. After a match, the only permitted mutation is the task-record close transition in step 7.
2. For modes other than `already-complete`, Standard/Large development activates `task-record` to open a `retro` checkpoint even when it produces no lesson. Small/recorded review/debug/analysis opens `retro` only when a lesson candidate/event exists.
3. During retro, activate `lesson-select` only when a qualifying lesson candidate/event exists; otherwise do not load lesson history merely for ceremony. Close the retro checkpoint when used. Finish every lesson write before capturing the verification subject.
4. For `targeted`, `changed`, or `full`, activate `task-record` to capture and persist the next verification subject and open `verify` in the same transition. A Large task runs exactly one final `full` gate for that captured subject; earlier affected checks remain stage evidence and never substitute the final gate. Activate `verify` exactly once at that scope, then close `verify` with the real evidence. On failure, leave the task active and return the evidence to the owning task context. Evidence stays append-only; the next correction captures a new subject before exactly one new final-gate attempt. Preserve both the subject and row. On success, check the persisted subject again immediately before close; a mismatch blocks closure. `verification_subject check` proves subject immutability, not that an earlier test ran for this subject.
5. `none` is valid only when no product/executable change requires final verification; validate the durable artifact/record itself as applicable. It has no verification subject.
6. Before closing a Standard/Large or milestone task, determine the product invariants affected by the task spec, changed paths, and declared result, using the product invariant register as the status source. With no product invariant register, list no invariants and never announce an invariant or milestone as met. The `Done` report distinguishes task completion from product state: list affected `unmet` and `deferred-by-decision` invariants with their evidence, and never announce a milestone as satisfying a blocking invariant whose status is not `met`. Passing local tests never flips an invariant status.
7. Activate `task-record` to perform the close transition and validation. For a verification-dependent close, this task-record-only mutation follows a successful subject check and must not change any subject path. This skill does not maintain a second task-record schema.
8. After the close transition succeeds, archive the closed task's handoff: move `.agents/handoffs/<task-id>.md` to `.agents/handoffs/archive/` unchanged, creating the directory when needed. Skip when no such file exists. This move is the only permitted post-closure mutation and must not touch any other file.
9. Close the recorded task before composing the final `Done` response. After this skill finishes, follow `Completion report` in AGENTS.md, using the actual validation evidence from this closure.

Do not add cleanup, refactoring, another review round, or new scope during closure.
