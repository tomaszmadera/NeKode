# Spec-driven development workflow

This workflow owns spec-driven development that keeps a durable task record, under one specification and one
plan. A Standard task has exactly one independently demonstrable stage; a Large task has two or more. Their
implementation ownership differs as defined below; every other rule applies to both.

- Activate `task-record` before broad discovery, then inspect repository and Git evidence. With more than one stage, refine stage boundaries before approval.
- Use `task-record` to keep current step and Timing aligned with named pipeline phases; other skills do not maintain a competing task-state format.
- Activate `lesson-select` only after an unexpected operational error, user correction, required-tool unavailability needing another method, a deterministic repository event mapped to a lesson domain, or a known lesson id/hint from state, handoff, or evidence. Do not inspect the index for a candidate.
- Activate `specification`, then `task-plan`. A multi-stage plan lists every stage up front as a compact index.
- Obtain user approval of the plan before preflight or product edits, then activate `preflight`.
- Before starting an extra implementer or independent reviewer, read `.agents/workflows/references/extra-session.md`.
- Every Large stage uses an extra implementer whenever implementation or correction work is active. Main remains the coordinator and does not implement or correct a Large stage. Start a bounded extra implementer before implementation begins. For Standard, Main implements or corrects work that fits in remaining context. For Standard, select an extra implementer only when the current work will not fit. Give an extra implementer the shared artifacts and first action; do not ask for permission to use the required extra session. Main does not concurrently edit a stage owned by an extra implementer. If a required implementer session cannot start, activate `handoff` and report that a distinct implementer session is required to continue.
- For each stage, open `implement:<stage>` through `task-record`, activate `implement` for that stage only, and receive its changed paths, evidence, failures, decisions, and unfinished actions. Close that row only after implementation and self-review finish. Then run the independent review gate below; complete the stage before advancing. If implementation is incomplete, resume the same stage through its required owner or handoff, rather than adding a stage for remaining tokens.
- Prefer one extra session for the review gate and never satisfy an independent-review requirement by self-reviewing the implementation. Main must not review its own diff. After any extra implementer has terminated, start exactly one reviewer as a **subagent** and do not ask whether to spawn; it returns findings and terminates before corrections begin. If no reviewer session can be started at all, including the same-agent subagent fallback defined in `.agents/workflows/references/extra-session.md`, activate `handoff` and report that a distinct reviewer session is required to continue.
- The coordinator opens `review:<stage>` through `task-record` before the reviewer starts and closes it after the review returns and the reviewer terminates. The reviewer writes neither a record nor `review.md` nor a Timing row. When blocking findings exist, the coordinator opens `correction:<stage>`. For Large, start a fresh bounded extra implementer in the freed slot to correct the findings. For Standard, Main corrects findings that fit in remaining context; start a fresh bounded extra implementer only when the correction will not fit. The correction owner repeats affected checks and complete diff self-review, then terminates if it is an extra implementer. The coordinator closes correction and opens another review row for re-review.
- Allow at most two correction/re-review rounds per stage. If independent review is unavailable or still blocking after the second re-review, preserve evidence with `handoff` and surface the blocker rather than treating review as passed.
- A stage is a demonstrable/testable slice, not a context-window partition. Context pressure loads `.agents/workflows/references/context-succession.md` and activates `handoff` for the unfinished current stage or recovery; it does not create a new stage, task, spec, or plan.
- Wait between stages only when the approved plan marks a consequential manual gate.
- After the last stage passes, activate `task-close` with final verification `changed` for a single-stage task, raised to `full` for a multi-stage task or when the changed surface, migration/security/public-contract/integration impact requires broader evidence. Capture the immutable verification subject after the last change, correction, documentation, lesson, and review; earlier affected checks remain stage evidence and never substitute that final gate. If that verification fails, keep the failed `verify` evidence and do not add a stage. Open unscoped `correction` and `review` rows; correct the current final diff through the same Standard/Large owner rules, then run independent review of that corrected diff. After review passes, capture a new verification subject for the corrected diff, then retry the same verification once on a new `verify` row without altering failed evidence. If that retry fails, repeat this loop with a fresh two-round count. After a passing retry, activate `task-close` with `already-complete`. If review is unavailable or still blocking after the second re-review, `handoff` the unfinished recovery rather than a stage.
